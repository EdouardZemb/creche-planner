Objectif : adresser le mail récap hebdo (et futures notifs) **aux parents du foyer** au lieu
de l'adresse globale `NOTIF_EMAIL_PARENT`. Modélisation propre, multi-familles. Web push
**hors périmètre** mais modèle compatible (parent = futur propriétaire de l'abonnement push).

**Doc de conception** : `.claude/plans/parents-foyer-modelisation.md` (état des lieux vérifié,
modèle de données, fork d'identité, plan PR, impacts exhaustifs).

**Décisions de cadrage actées (2026-06-26, via AskUserQuestion)** :

- **(B) Identité / login** (pas contact-only) : les parents deviennent des identités
  authentifiables avec **autorisation par foyer** (un parent ne voit que SON foyer).
- **(B1) Cloudflare Access** : on fait confiance à l'email validé par CF Access ; le BFF
  **valide le JWT `Cf-Access-Jwt-Assertion`** (JWKS/team domain/`aud`, jamais le header brut
  spoofable) et mappe `email → parent → foyer`. Pas d'auth applicative (B2 rejeté, redondant).
- **(b-ii) provisioning admin** : seul un **rôle admin** (allowlist `ADMIN_EMAILS` vs email
  CF) crée les foyers et rattache les parents. L'écran web « créer un foyer » devient
  **gated admin** ; un parent sans foyer voit « contactez l'administrateur ».
- **Email unique PAR FOYER** (`UNIQUE(foyer_id, lower(email)) WHERE actif`) depuis le lot 5 foyer (migration svc-foyer 0003, cf. [[feature-qualite-foyer-onboarding]]). ⚠️ **PLUS globalement unique** — l'ancienne note « `UNIQUE(lower(email))` global » est PÉRIMÉE. Conséquence : un même humain a un `parent.id` différent par foyer → cf. limitation multi-foyer dans [[plan-qualite-profil-communication]].
- **Accès notifications→parents = projection NATS** (pas HTTP+Pact) : notifications s'abonne
  au stream `FOYER` (déjà publié par svc-foyer, déjà consommé par tarification) et projette
  une table locale `foyer_parent`. Zéro nouveau contrat Pact.

**Modèle** : table dédiée `parent` dans svc-foyer (`id, foyer_id` FK cascade, `prenom?/nom?`,
`email`, `principal`, `ordre`, `actif`, timestamps). Events outbox `foyer.ParentAjoute/
Modifie/Retire.v1` sur stream `FOYER`. Récap regroupé **par foyer** (vs 1 mail/contrat
aujourd'hui) ; repli `NOTIF_EMAIL_PARENT` + warning si foyer sans parent.

**Plan en 8 PR** (principe : modèle+destinataires d'abord, enforcement auth EN DERNIER
derrière flag, activé après back-fill — ne jamais verrouiller la prod) :

1. svc-foyer : modèle `parent` + CRUD + events + `GET /foyers?parentEmail=` + migration générée.
2. BFF/OpenAPI : CRUD parents (sans enforcement) ; maj `gateway.openapi.ts` + test « N routes » + régen `openapi-types.gen.ts`.
3. web : UI parents dans `FoyerFormPage`.
4. svc-notifications : projection `foyer_parent` (consumer durable `notifications-foyer`) + récap groupé + repli. **← objectif fonctionnel atteint ici, sans toucher l'auth.**
5. BFF : guard d'identité B1 (validation JWT CF), observe-only (pose l'identité, ne refuse rien).
6. admin (guard `ADMIN_EMAILS`) + écran création gated + sélecteur foyer web (0/1/N) + back-fill.
7. enforcement guard d'appartenance 403 sur toutes routes portant un `foyerId`, derrière flag.
8. config/déploiement/doc : déprécier `NOTIF_EMAIL_PARENT`, config CF Access + `ADMIN_EMAILS`, doc 06.
